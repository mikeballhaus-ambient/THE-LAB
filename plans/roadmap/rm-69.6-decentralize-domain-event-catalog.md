# rm-69.6 — Lab domain event catalog architecture (active programme)

**Status:** ✅ **Complete** (2026-11-18) — **rm-71** may proceed after owner `test:pipeline` sign-off  
**Owner decision (Nov 2026):** Current monolithic `LAB_DOMAIN_EVENT_CATALOG` is **not acceptable for OSS** — contributors with many apps cannot maintain a shared 755-line file or giant PRs.  
**Roadmap:** [docs/roadmap.md](../../docs/roadmap.md)

---

## Problem statement

| Today | Failure mode at scale |
|-------|------------------------|
| Every app’s event **metadata** lives in `src/shared/config/lab-domain-event-catalog.ts` | Fork adds 50 apps → every event edit touches **platform** file → merge hell |
| App scaffold (`generate-app`, `app_management_create_app`) does not register events | Events are an afterthought; docs say “edit the monolith” |
| Runtime + client import the same static array | No registration boundary aligned with **app ownership** |

We pay now for not requiring **per-app registration** when the catalog app ecosystem was designed.

---

## Design principles (locked)

1. **Own where you publish** — each app (or platform area) **authors** its catalog rows beside its code.
2. **Register, don’t concatenate** — platform exposes a **registry** that **aggregates** at bootstrap and on app lifecycle changes; no human-edited god file.
3. **Git is contract** — registration modules are in the app tree (reviewable in PRs scoped to that app).
4. **DB is runtime materialization** — platform SQLite holds the merged catalog for API/UI; idempotent sync from registrations.
5. **App Management + App Builder are part of the loop** — scaffold includes an empty manifest; agents/docs tell authors to fill it when they add `publishLabDomainEvent`.
6. **CI per app** — publisher test uses **that app’s manifest only**; global CI checks uniqueness and discovery.

## Target architecture

```text
Per app (catalog / hybrid with back-end):
  src/apps/<dir>/shared/lab-domain-events.manifest.ts
    export const LAB_DOMAIN_EVENTS_MANIFEST: readonly LabDomainEventCatalogEntry[] = [ ... ];

Platform:
  src/backend/lab-events/domain-event-catalog-registry.ts
    registerAppManifest(appId, entries)
    registerPlatformManifest(entries)   // approvals, rules, requirement-sweep
    buildStaticCatalog()                // for CI + optional client bundle
    syncToDatabase(db)                  // UPSERT lab_domain_event_catalog

Persistence (main platform DB):
  lab_domain_event_catalog
    event_type PK, source_app_id, publisher_kind, label, description,
    payload_fields_json, registered_at, content_hash

Runtime:
  GET /api/platform/lab-events/catalog
    SELECT from DB + merge observed types from lab_domain_events (unchanged semantics)

Client (phased):
  Phase A — Workflow Studio already loads catalog API
  Phase B — replace direct LAB_DOMAIN_EVENT_CATALOG imports in validators with API or build-time generated JSON from registry scan
```

**Naming:** `*.manifest.ts` (not `.catalog.ts`) to stress **registration**, not a second monolith.

## App lifecycle integration

| Step | Behaviour |
|------|-----------|
| `npm run generate:app` / `app_management_create_app` | Scaffold `shared/lab-domain-events.manifest.ts` with `export const LAB_DOMAIN_EVENTS_MANIFEST = [] as const` + comment block linking to lab-domain-events.md |
| App first backend start / platform bootstrap | `registerAppManifestFromDisk(appId)` — dynamic import or pre-built index |
| `app_management_update_app` | No change unless we add optional **validate_manifest** in later phase |
| Platform bootstrap | `DomainEventCatalogRegistry.syncAll()` — all apps + platform manifests → DB |
| Delete app | Remove rows where `source_app_id = appId` |

**App Builder (Sidecar):** extend consultation checklist — “If this app will publish domain events, list entity/action pairs; scaffold manifest entries (declared intent) before merge.”

**Future (optional):** MCP `app_management_register_domain_events` upserts manifest snippet — only after file-based path is stable.

## Platform-only events

Keep in **`src/platform/lab-domain-events/`** (or `src/shared/config/platform/`) as small modules:

- Rules / approvals / ledger publishers
- Requirement-sweep (time-derived) entries — still `publisherKind: 'platform'`, documented once, registered via `registerPlatformManifest`

No catalog-app rows in platform files except CRM integration bundle if still shared.

## What we are NOT doing in v1

- User-editable catalog rows in Settings UI (DB is materialized from git manifest only)
- Runtime registration without a file in the app repo (no “declare only in DB” for OSS)
- Removing publisher CI — it becomes **per-app manifest** scoped
