# rm-68.3 — UI automation discovery audit & refactor

**Status:** ✅ Closed (2026-11-12) — [closeout](../../docs/archive/programmes/rm-68.3/EXECUTOR-CLOSEOUT.md)  
**Roadmap:** [docs/roadmap.md](../../docs/roadmap.md) (rm-68.3)  
**Related:** rm-13 / rm-17 (UI automation), rm-57 (Sidecar), rm-68.2 (DOM tagging), [lab-sidecar.md](../../docs/platform/lab-sidecar.md)

## Problem

Users and agents expect **`searchPattern` to narrow discovery** to a small, relevant set. In practice, agents still paginate hundreds of nodes, miss the right control (e.g. catalog Launch shows label **"Launch"** not the app name), time out, or pass **fragile CSS `target`s** to `ui_automation_element_action` that do not resolve to the same node as discovery.

### `searchPattern` root cause (P0)

Tool copy said “regex”, so agents passed **invalid regex** (`Workflow Studio` with unescaped space is fine as regex actually...) — worse: **`[data-appname="CRM"]` as regex** (character class), **quoted strings**, and **CSS selectors** that can never match button labels. The handler used `new RegExp(pattern, 'i')` with no literal fallback and **dropped `resultMessage` on zero hits** before the model. **rm-68.3 ships the compiler first** (`compileUiAutomationSearchPattern` — literal substring by default, CSS value extraction, `regex:` opt-in); remaining work is discover→act identity and context profiles.

Symptoms (2026-11-12 Workflow Studio launch):

- Unscoped or overly broad selectors inside `contextArea` (e.g. every `div[class]`) inflate `totalCount`.
- `searchPattern` not matching the attributes agents are told to use (`data-appname`, `data-app-id`, `aria-label`).
- Discover → act uses **reconstructed selectors** (tag + first classes + all data-*) with no stable **element identity** across tool calls.
- Tool result truncation / formatting may hide the attrs needed to click the right button.

rm-68.2 fixes **DOM tagging** on lists and catalog launches; rm-68.3 fixes the **discovery and action pipeline** so tagging pays off.

## Goal

**Targeted discovery by default:** `searchPattern` + `contextArea` return a small set of elements with **stable, replayable identities**. **`ui_automation_element_action`** must act on **the same element** the agent selected from discovery (no second-guessing selectors).

## Principles

| Principle | Meaning |
|-----------|---------|
| **Filter first** | Apply `searchPattern` (and context scoping) before pagination; empty pattern + huge scope is an anti-pattern documented to agents |
| **Stable identity** | Each discovered element exposes an id agents can pass to action (see deliverables) |
| **Selector stability** | Prefer semantic `data-*` contracts (`data-lab-record-*`, `data-app-id`, `data-lab-catalog-action`) over class stacks |
| **Discover ⊆ Act** | Action resolution uses the same matching rules as discovery (shared builder / resolver) |
| **Measurable** | Regression tests: known DOM fixtures → discover → act → success without pagination |

## In scope

| Area | Work |
|------|------|
| **Audit** | End-to-end flow: MCP → socket → `UIAutomationHandler` → format/truncate → model → action → DOM. Document failure modes (timeout, regex errors, visibility, PrimeVue teleport). |
| **Discovery scoping** | Context-area profiles (catalog, settings, app shell, dialogs): allowed tags/roles, default `maxResults`, omit layout noise. Extend rm-68.2 catalog narrowing pattern platform-wide. |
| **Search contract** | Single helper for pattern matching; documented fields; invalid-regex handling; optional literal vs regex mode; tests for `data-app-id`, `aria-label`, record attrs. |
| **Target builder** | Unify `buildTargetSelector` priority (catalog launch, record actions, fallbacks); avoid selectors that change when class order changes. |
| **Discover → act bridge** | Add **`elementRef`** (or reuse deterministic `target` tier) on each `UIDiscoveryElement`; extend `element_action` to accept `elementRef` **or** `target` with server-side validation that one node matches. |
| **Agent ergonomics** | MCP tool descriptions, Sidecar appendix, `tool-failure-agent-guidance`, failure messages when `totalCount` is high without `searchPattern`. |
| **Performance** | 10s discover timeout vs large DOM; index or early-exit when `searchPattern` matches enough results. |

## Out of scope

- Replacing UI automation with REST for all app workflows (launch via API remains optional future).
- Playwright / smoke harness rewrite (may add one discover→act contract test).
- Game board pixel automation.

## Acceptance criteria

1. **Audit doc** in tracker: current behavior, gaps, and refactor checklist (signed by executor).
2. **Catalog launch** (and one list CRUD path): one discover with `searchPattern` returns ≤ few elements; action succeeds via `elementRef` or canonical `target` without pagination.
3. **`searchPattern` tests** cover app launch, record name, registry id, and invalid regex (graceful error).
4. **Discover → act integration test** (browser or handler fixture) proves same-element replay.
5. `npm run test:pipeline` green; roadmap **rm-68.3** closed; **rm-68** unblocked with discovery no longer a known gap.

## Phasing (suggested)

1. **Audit & metrics** — Instrument/log `totalCount`, duration, pattern hit rate; inventory context areas and selectors.
2. **Search + scope** — Context profiles; tighten default interactive queries; fix any filter-order bugs.
3. **Identity bridge** — `elementRef` generation, action resolver, schema + MCP params, deprecate-only docs for “guess a new selector”.
4. **Prompts & docs** — Sidecar, sysMsg pointers, operator note in [docs/platform/lab-sidecar.md](../../docs/platform/lab-sidecar.md) (or new `lab-ui-automation.md` if warranted).
