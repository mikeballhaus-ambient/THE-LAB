# rm-68.1 — Sidecar awareness for lab shell surfaces (Settings, About, Messages, …)

**Status:** ✅ Completed (closed 2026-11-12) — [closeout](../../docs/archive/programmes/rm-68.1/EXECUTOR-CLOSEOUT.md)  
**Roadmap:** [docs/roadmap.md](../../docs/roadmap.md) (rm-68.1)  
**Related:** rm-57 (Sidecar), rm-68 (prompt coherence), rm-50.4 (Messages), UI automation  
**Parent theme:** Agents should know **where the human is looking**, not only which catalog app is mounted.

## Problem

Sidecar context today covers **apps home**, **single/split app workspace**, and **full Laboratory** — plus optional `hostContext` from mounted apps. It does **not** describe when the user has **Settings**, **About THE-LAB**, **Messages (lab-comms)**, or other quick-nav overlays open.

Owners report agents (via Sidecar) **struggle to change Settings options** — the model lacks surface-specific instructions and UI automation scoping.

## Goal

When the user chats from Sidecar while a **non-app shell surface** is active, the backend system appendix should state:

- Which **surface** is open (e.g. Settings → Themes, Messages → thread with user X).
- How to act: **UI automation** selectors / `contextArea` hints, or **when to defer** to Settings APIs / MCP (personas, providers) vs clicking controls.
- **Role gates** (admin-only panels) where relevant.

Default behavior unchanged when only apps/catalog are visible.

## In scope (v1) — locked 2026-11-12

| Surface | Detection | Sub-context |
|---------|-----------|-------------|
| **Settings** | `showSettingsModal` | `activeTab` (`SettingsViewId`); Personas: `activePersonaTab` / property tab |
| **Messages** | `showMessagesModal` | `activePartnerId`, `openPartnerIds` |
| **Notifications** | `notificationsDialogVisible` | expanded group titles, bulk selection |
| **Quarks** | `quarksDialogVisible` | wallet dialog (no inner tabs v1) |
| **About** | `showAboutModal` | About topic tab |

Precedence: Settings → Messages → Notifications → Quarks → About. Omitted when `focusedAssistant` (full Laboratory).

**v1.1 (optional):** running-apps rail, catalog sidebar, modal stacking diagnostics.

**Out of v1:** force password change, loading dialog, Lab-only overlays when Sidecar unavailable.

## Out of scope

- Replacing Settings HTTP/MCP with automation for every control.
- Sidecar tool allowlist changes (separate from rm-68 integration/App Builder profiles).
- Full Laboratory transcript tool UI (rm-67.8).

## Technical approach (suggested)

1. **Context model** — Extend `LabSidecarViewContextInput` / `LabViewMode` (or add `labShellOverlay?: …` + `settingsTab?: string`) fed from `useLabDashboard` into `provideLabWorkspaceContext`.
2. **Prompt** — `formatLabSidecarSystemPromptAppendix()` blocks per surface (mirror apps_home guidance pattern in `format-lab-sidecar-system-prompt.ts`).
3. **UI automation** — Document `contextArea` values for Settings/Messages; add stable `data-lab-shell-*` or existing PT ids where missing.
4. **Tests** — `buildLabSidecarViewContext` + prompt snapshot tests for settings-open vs apps_home.
5. **Docs** — [lab-sidecar.md](../../docs/platform/lab-sidecar.md) “What the agent sees” table.

## Acceptance criteria

1. With Settings open on a known tab, Sidecar send includes appendix naming **Settings** + active tab.
2. Agent spot-check: user asks to toggle a **Themes** or **Personas** control — agent uses UI automation or correct MCP, not hallucinated app context.
3. About + Messages surfaces do not report `single_app` / focused app incorrectly.
4. Roadmap rm-68.1 marked complete after owner sign-off.

## Dependencies

- UI automation handler must remain able to target teleported Settings dialog (may already work — verify).
