## Intent (read this first)

rm-72.2 is **not** “call `ensureAccountWithAccrual` once from the bus.” It is the **first multi-step platform workflow** that forces **new Workflow Studio action kinds**, wired with the **existing `if_condition` router**, to implement a real product path: **login → read wallet → decide → credit → toast**.

That graph is the **guinea pig** for platform step expansion (canvas, schema, runner, dry-run, MCP summaries, demo seed, CI). Virtual bank rules stay in `lab-virtual-bank-repository`; the workflow **orchestrates** them through discrete steps authors can see and fork.

## Part A — Trigger event

| Field | Value |
|-------|--------|
| `eventType` | `platform.auth.session.established` |
| `sourceAppId` | `platform-auth` |
| `publisherKind` | `platform` |

Publish once per **new** `lab_sessions` row via shared `afterLabSessionCreated` (HTTP login, OIDC callback, socket login). Not on cookie resolve / reconnect.

**Payload (v1):** `userId`, `authMethod`, `providerKey`, `utcDate`, optional `sessionId`.

Manifest in `platform-lab-domain-events.manifest.ts`; optional `LAB_AUTH_SESSION_EVENTS=0`.

## Part B — New workflow actions (platform steps)

All four are **new** `step.kind` values (types, Zod schema, `lab-workflow-step-runner`, canvas palette + defaults, Workflow Studio instructions, regression tests). Group: **Virtual bank / Quarks**.

### B1 — `virtual_bank_get_wallet`

**Job:** Read wallet state for workflow items **without posting accrual** (read-only for branching).

**Input:** Item JSON must resolve `userId` (path config, default `userId`).

**Output (replaces / merges into item JSON):** e.g.

| Field | Meaning |
|-------|---------|
| `balance` | Current Quarks balance (account created with opening balance if missing) |
| `lastDailyAccrualDate` | UTC `YYYY-MM-DD` |
| `dailyAccrualAmount` | Policy constant (500) |
| `balanceCap` | Daily accrual cap constant |
| `dailyAllotmentEligible` | **boolean** — would `ensureAccountWithAccrual` credit &gt; 0 today? |
| `projectedAllotmentDelta` | Quarks that **would** be credited (0 if not eligible) |

**Implementation note:** Add repository/service helper `evaluateDailyAllotmentEligibility(labUserId)` mirroring the **decision math** in `ensureAccountWithAccrual` without mutating (or read account + pure function). Do **not** use `getAccountView()` here — that accrues as a side effect and makes the IF node pointless.

### B2 — `if_condition` (existing)

**Job:** Branch on eligibility using **standard** workflow conditions (`payload_equals`, `payload_less_than`, etc.) on the enriched item — e.g. `dailyAllotmentEligible` equals `true`. Authors may also compare `lastDailyAccrualDate` to `utcDate` from the trigger payload for teaching graphs.

No new step kind; document the **pattern** in the demo and Studio instructions.

### B3 — `virtual_bank_credit_daily_allotment`

**Job:** Apply **canonical** daily accrual for the resolved `userId` (same ledger semantics as today: `daily_accrual` reason, cap, catch-up days).

**When:** Typically on the **true** branch after B1 + IF.

**Must** call shared repository accrual path (extract from `ensureAccountWithAccrual` if needed) — **not** a hand-entered delta in the graph.

**Output on item:** `accrualApplied`, `accrualDelta`, `balanceAfter`, `ledgerEntryId` (when credited); zeros / omitted when nothing to credit (idempotent no-op).

**Idempotency:** If login workflow and later wallet GET both run, at most one accrual per UTC day (existing tests remain the contract).

### B4 — `show_user_toast` (new)

**Job:** Push a **PrimeVue-style toast** to the signed-in user’s dashboard session (not bell notifications).

**Config:** `userIdPath`, `severity` (`success` | `info` | `warn` | `error`), `summary`, `detail` (template strings with `{{payload.*}}` / item fields — same resolver as `notify_users`).

**Runtime:** New platform socket fan-out (e.g. lab-events namespace `lab_events:toast` or dedicated platform event) → shell handler calls global toast bus (`useToast` / `useLabAppToast` pattern). User must be online on platform socket; offline users skip toast (document fail-open).

**Branches in demo:**

- **Success** (after credit, `accrualDelta` &gt; 0): success toast using `LAB_QUARKS_CURRENCY.dailyAccrualToastSummary` + amount in detail.
- **Skipped** (IF false): silent — no toast on every login refresh when already credited or at cap.
- **Failure** (credit step error / run node failed): error toast on false/error path or dedicated branch reading step `detail` — exact wiring in demo graph; runner must surface credit failures in step output for downstream copy.

## Part C — Guinea pig workflow (seed)

**Id:** stable demo UUID (new row in `demo-workflow-seed-catalog.ts`)  
**Name:** `Platform: Quarks daily allotment on login`  
**Scope:** `global`  
**Trigger:** `platform.auth.session.established`  
**Enabled:** product decision (recommend **enabled** on demo pack so the guinea pig is exercisable out of the box).

**Graph (logical):**

```text
[Trigger: session.established]
    → [virtual_bank_get_wallet]     userId from payload
    → [if_condition]                dailyAllotmentEligible == true
         └─ true  → [virtual_bank_credit_daily_allotment]
                        → [show_user_toast] success
    (false branch: end — no toast on repeat login / already at cap)
```

Optional: on credit step failure, workflow run shows failed node; add error toast node only if runner exposes a failure port or a follow-on `if_condition` on `accrualDelta` / `accrualApplied` — prefer **explicit** success vs no-op vs error in step output JSON for teaching.

Bump `DEMO_AUTOMATION_DEFINITION_REVISION` when definition changes.

## Part D — Relationship to GET `/api/platform/virtual-bank`

| Concern | Policy |
|---------|--------|
| Wallet GET still accrues today | **Yes (v1)** — fallback if workflow disabled; same idempotency |
| rm-72.2 replaces GET accrual | **No** — workflow is the **visible** automation; GET remains safety net |
| Toast on GET path | Unchanged (`accruedThisRequest` in client); login workflow adds **workflow-driven** toasts |
